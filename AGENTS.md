# Mini Wiki contributor guidance

Before adding, integrating or materially refining a topic, read:

- [Design principles and acceptance requirements](docs/design-principles.md) — the canonical design baseline, in Chinese.
- [Architecture](docs/architecture.md) — runtime, registration, localization and delivery contracts.
- [Source boundaries](SKELETON.md) and the affected topic's README — ownership and scientific limitations.

Apply the requirements to the changed scope, not as permission to rewrite unrelated topics.
Keep this file a short entry point; maintain detailed principles in the canonical document.

## Working rules

- Build a coherent learning journey, not merely a menu combining old demonstrations.
- Preserve causal order, object/site identity and meaningful experiment state across views.
- Distinguish observation, inference, model output and illustrative geometry; do not invent certainty or physical precision for visual polish.
- Keep scientific models and content topic-owned. Share presentation only where the responsibility is genuinely common.
- Maintain equivalent scientific qualifications in Chinese and English. Check current schemas/tests before changing authored-content structure.
- Preserve valid legacy links when removing duplicate catalog entries. Inspect current routing and `parentTopic` contracts first.
- Protect existing dirty work and coordinate overlapping paths. Local edits do not authorize commits, pushes or deployment.
- Validate the affected contract proportionately. UI work needs actual browser checks; new topics and broad integrations require the repository gates. Documentation-only work needs source/link checks, not an unrelated runtime rebuild.

Report separately what was changed, tested, visually inspected, committed and deployed.
Existing implementations are references, not proof that every design requirement has already been met.
